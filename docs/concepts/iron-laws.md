# Iron Laws

Declutter의 세 가지 철칙은 안전한 리팩토링을 보장합니다. 이 원칙들은 협상의 대상이 아닙니다.

---

## 왜 Iron Laws인가?

레거시 코드 리팩토링은 위험합니다. 작은 변경이 예상치 못한 곳에서 버그를 일으킬 수 있습니다. Iron Laws는 이러한 위험을 최소화하기 위한 안전장치입니다.

> "먼저 이해하지 않고 변경하면, 고치는 것보다 더 많이 망가뜨립니다."
> — Michael Feathers, Working Effectively with Legacy Code

---

## 세 가지 Iron Laws

```
╔═══════════════════════════════════════════════════════════════════╗
║  NO REFACTORING WITHOUT ASSESSMENT FIRST                          ║
║  NO CODE CHANGE WITHOUT TEST HARNESS FIRST                        ║
║  NO COMPLETION WITHOUT VERIFICATION FIRST                         ║
╚═══════════════════════════════════════════════════════════════════╝
```

---

## 1. 평가 없이 리팩토링 금지

**"코드를 이해하기 전에 변경하지 않는다"**

### 의미

리팩토링을 시작하기 전에 반드시 코드베이스를 평가해야 합니다:
- 코드 스멜 탐지
- 복잡도 분석
- 의존성 매핑
- 리스크 평가

### 올바른 접근

```bash
# 1. 먼저 평가
/assess src/legacy/

# 2. 리포트 검토
# 3. 우선순위 결정
# 4. 그 다음 리팩토링
/declutter src/legacy/problematic.py
```

### 잘못된 접근

```bash
# ❌ 평가 없이 바로 리팩토링
/declutter src/legacy/

# ❌ "문제가 뭔지 알아" 하고 바로 시작
# 숨겨진 의존성을 놓칠 수 있습니다
```

### 흔한 변명과 반박

| 변명 | 반박 |
|------|------|
| "문제가 뻔해 보인다" | 평가는 숨겨진 문제를 드러냅니다 |
| "시간이 없다" | 평가 없이 하면 더 많은 시간이 걸립니다 |
| "작은 변경이라 괜찮다" | 작은 변경도 큰 영향을 줄 수 있습니다 |

## 2. 테스트 없이 코드 변경 금지

**"특성화 테스트로 동작을 먼저 캡처한다"**

### 의미

코드를 변경하기 전에 현재 동작을 테스트로 기록해야 합니다:
- 특성화 테스트 작성
- 엣지 케이스 포함
- 사이드 이펙트 검증

### 특성화 테스트란?

특성화 테스트는 코드가 **"해야 하는 것"**이 아니라 **"실제로 하는 것"**을 기록합니다.

```python
def test_process_order_current_behavior():
    """특성화 테스트 - 리팩토링 전 현재 동작 기록"""
    # Arrange
    order = {"user_id": 123, "items": [{"id": 1, "qty": 2}]}

    # Act
    result = process_order(order)

    # Assert - 현재 동작 (버그가 있더라도)
    assert result["status"] == "ok"
    assert result["total"] == 200  # 현재 계산 결과
```

### 올바른 접근

```
1. 테스트 하네스 생성
2. 모든 테스트 통과 확인
3. 하나의 원자적 변경
4. 테스트 실행
5. 통과하면 커밋
6. 다음 변경으로
```

### 잘못된 접근

```bash
# ❌ 테스트 없이 변경
"이 코드는 간단해서 테스트 필요 없어"

# ❌ 변경 후 테스트 작성
"나중에 테스트 추가하면 되지"

# ❌ 기존 테스트만 믿기
"기존 테스트가 충분할 거야"
```

### 흔한 변명과 반박

| 변명 | 반박 |
|------|------|
| "기존 테스트가 있다" | 특성화 테스트가 리팩토링 대상을 직접 커버하는지 확인하세요 |
| "테스트하기 너무 복잡하다" | 복잡하다면 더욱 테스트가 필요합니다 |
| "테스트가 느리다" | 느린 테스트 > 깨진 리팩토링 |
| "단순한 리네임이다" | 리네임도 임포트를 깨뜨립니다. 테스트하세요 |

## 3. 검증 없이 완료 선언 금지

**"모든 테스트 통과를 확인한다"**

### 의미

리팩토링이 끝났다고 생각해도 반드시 검증해야 합니다:
- 전체 테스트 스위트 실행
- 새로운 스멜이 없는지 확인
- 동작 보존 검증
- 품질 개선 확인

### 올바른 접근

```
1. 모든 테스트 실행
2. 테스트 커버리지 확인
3. 스멜 스캔 실행
4. 전후 비교
5. 검증 완료 후 완료 선언
```

### 검증 체크리스트

```markdown
## 테스트 검증
- [ ] 모든 유닛 테스트 통과
- [ ] 모든 통합 테스트 통과
- [ ] 테스트 커버리지 유지 또는 개선

## 동작 보존
- [ ] 퍼블릭 API 변경 없음
- [ ] 에러 처리 보존
- [ ] 엣지 케이스 처리 유지

## 품질 개선
- [ ] 대상 스멜 제거됨
- [ ] 새로운 스멜 없음
- [ ] 복잡도 감소
```

### 흔한 변명과 반박

| 변명 | 반박 |
|------|------|
| "테스트가 통과하니까 됐다" | 전체 스위트를 실행했나요? 커버리지는요? |
| "로컬에서 잘 동작한다" | CI에서도 확인하세요 |
| "작은 변경이라 검증 필요 없다" | 작은 변경도 검증이 필요합니다 |

---

## Iron Laws 위반의 결과

Iron Laws를 무시하면:

1. **평가 없이 리팩토링**
   - 숨겨진 의존성 발견 못함
   - 잘못된 우선순위
   - 더 많은 버그 도입

2. **테스트 없이 변경**
   - 동작 변경을 인지하지 못함
   - 롤백 불가능
   - 디버깅 악몽

3. **검증 없이 완료**
   - 깨진 코드 배포
   - 고객 영향
   - 신뢰 상실

## 예외는 없다

다음과 같은 생각이 들면 **멈추세요**:

- "이건 간단한 변경이라 괜찮아"
- "시간이 없어서 테스트는 나중에"
- "확실히 동작하니까 검증은 스킵"
- "기존 테스트로 충분해"
- "이건 예외적인 상황이야"

이러한 생각은 **모두 위험 신호**입니다.
